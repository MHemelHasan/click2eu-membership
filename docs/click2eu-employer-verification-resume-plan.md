## 1. Objective

Implement three connected capabilities inside the Click2EU Membership
plugin:

1.  Employer-only account verification and administrator approval.
2.  A redesigned, Employer-only Resume Directory with custom search and
    listing UI.
3.  A Contact Candidate workflow on single Resume pages, replacing the
    existing Invite Candidate action.

Candidate registration and Candidate membership behavior must remain
unchanged. Do not enable Cariera's global user approval if it also
blocks Candidates.

The implementation must preserve the existing v0.7.4 membership,
access-control, notification, WooCommerce HPOS, renewal, expiration, and
Phase-1 route-policy behavior.

## 3. Architecture decisions

### 3.1 Implement Employer approval inside Click2EU Membership

Do **not** enable a global Cariera approval option if it applies to both
Candidate and Employer roles.

Create a dedicated Employer verification module in the Click2EU plugin.
Suggested class:

`includes/class-click2eu-employer-verification.php`

Suggested user-meta keys (use constants in the class):

-   `_click2eu_employer_verification_status`
-   `_click2eu_company_name`
-   `_click2eu_company_registration_number`
-   `_click2eu_employer_verification_submitted_at`
-   `_click2eu_employer_verification_reviewed_at`
-   `_click2eu_employer_verification_reviewed_by`
-   `_click2eu_employer_verification_admin_note`

Allowed statuses:

-   `pending`
-   `approved`
-   `rejected`
-   `suspended`

A missing status on an existing Employer must be treated as **unverified
/ pending**, not implicitly approved. This is important for safe
migration and existing accounts.

Candidate users must never be assigned or checked against Employer
verification status.

### 3.2 Login policy

Requirement: a newly registered Employer must not be able to log in
until an administrator approves the account.

Implement a narrowly scoped authentication check using the WordPress
authentication pipeline (for example, `wp_authenticate_user`) and return
a clear `WP_Error` only when all of the following are true:

-   The authenticating user has the `employer` role.
-   Employer verification status is not `approved`.

Do not block: - Candidate login. - Administrator login. - Other
WordPress roles. - Password reset requests. - Registration submission
itself.

The login error should distinguish pending, rejected and suspended
states without exposing private administrator notes.

Also guard already-authenticated Employer sessions. A user who was
logged in before an administrator suspends the account must lose
protected Employer capabilities on the next request. Authentication-only
blocking is not sufficient.

### 3.3 Admin review UI

Add an Employer Verification screen under the existing
`WP Admin > Click2EU Memberships` menu.

The screen should show a paginated table with:

-   Employer user ID and display name.
-   Account email.
-   Company name.
-   Company registration number.
-   Submission date.
-   Current verification status.
-   Review actions.

Actions: - Approve - Reject - Suspend - Optionally restore a
rejected/suspended account to Pending for a fresh review.

Security: - Require `manage_options`. - Use a dedicated nonce for every
state-changing action. - Validate user ID and ensure the target user has
the Employer role. - Sanitize and escape all displayed values. - Record
reviewer ID and timestamps. - Record an optional internal admin note;
never show it to the Employer. - Use Post/Redirect/Get after an action
and show an admin notice. - Actions must be idempotent and must not
create duplicate review records.

Approval should not grant Candidate membership, alter WooCommerce
orders, or change Candidate membership ledger data.

### 3.4 Registration field integration

The current plugin's
`Click2EU_Cariera::validate_cariera_registration_role()` validates the
submitted role but does not itself render or persist the company
registration fields.

The user reports that the Employer registration form already contains: -
Company Name - Company Registration Number

Before implementation, inspect the active registration form provider and
existing custom code to identify exactly where these fields are rendered
and saved. Preserve the current field names and validation behavior
where possible.

Requirements: - Fields are required only for Employer registration. -
They are not required or displayed for Candidate registration. -
Validate and sanitize values server-side; browser `required` attributes
are not enough. - Persist the values to the new Click2EU user-meta
keys. - On successful Employer account creation, initialize verification
status to `pending`. - Do not trust a user-submitted verification
status. - Do not allow registration requests to set the status to
`approved`. - Preserve the existing Cariera registration response format
and AJAX behavior. - Prevent duplicate/ambiguous registration
processing.

If the fields currently live in a separate plugin or child-theme
snippet, document the existing source and migrate the integration
carefully. Do not silently create a second set of fields.

## 4. Centralized Employer authorization

Update `Click2EU_Auth` with a helper such as:

`is_approved_employer( $user = null )`

It must require: 1. A real logged-in/valid WP_User. 2. The `employer`
role. 3. Exact verification status `approved`.

Do not change `is_employer()` semantics unless every existing call site
has been audited. Role identity and approval state should remain
separate concepts.

Update `Click2EU_Route_Policy`:

-   Replace Employer role-only privileged access with administrator OR
    approved Employer.
-   A pending/rejected/suspended Employer must not be treated as
    privileged.
-   Preserve the existing Candidate effective-membership rules.
-   Preserve administrator access.
-   Keep existing company ownership and published-company checks.
-   Ensure protected Resume routes, Resume listing AJAX, REST, search
    queries, contact submission and download endpoints all apply the
    same approved Employer check.

Important: `is_privileged_actor()` is used across jobs, companies,
resumes and other Phase-1 access decisions. Audit all callers before
changing it. An unapproved Employer must not inherit the current
Employer bypass for job/company routes.

For a logged-in but unapproved Employer, show a dedicated
verification-required page/message (or a configured safe account
destination). Do not redirect them to Join Us, because Join Us is a
Candidate membership purchase route.

Guests should continue to use the existing authentication redirect
behavior.

## 5. Resume Directory: new plugin shortcode

Create a new shortcode:

`[click2eu_resume_directory]`

After the new implementation is accepted, replace `[resumes]` on the
existing Resume WordPress Page with `[click2eu_resume_directory]`.

Do not create a new WordPress Page unless the current page is missing.
Do not create a WordPress Page for every single Resume.

### 5.1 Access rules

The directory must be visible only to approved Employers and
administrators.

-   Guest: redirect to the mapped login/registration page, preserving a
    safe local return URL.
-   Candidate: deny access, even if the Candidate has an Active
    membership.
-   Pending Employer: show verification-pending message.
-   Rejected/Suspended Employer: show appropriate access-denied state.
-   Approved Employer: show directory.
-   Administrator: may inspect the directory for moderation/support.

Also protect the AJAX/REST/data endpoint. Hiding the shortcode output is
not sufficient.

### 5.2 Data source

Use the existing WP Job Manager -- Resume Manager `resume` post type and
its existing metadata/taxonomies. Do not create a duplicate Candidate or
Resume database.

Only show: - `post_type = resume` - `post_status = publish` - Resume
author has an effective Active Click2EU Candidate membership - Resume
author is a Candidate - Resume has not been deleted or otherwise
invalidated

Reuse `Click2EU_Route_Policy::active_candidate_ids()` or a safe
repository/query helper based on the existing membership ledger. Avoid
one SQL query per Resume card (N+1 queries).

Preserve the current membership rule that a Candidate's Resume is
visible only while their membership is effective Active.

### 5.3 Search and filters

Create a clean, minimal, responsive search area. Recommended first
release fields:

-   Keyword (Resume title, Candidate professional title, description and
    supported skill terms where practical).
-   Location.
-   Resume Category, only if Resume Categories are enabled and
    available.
-   Optional Skill filter if the installed Resume Manager configuration
    exposes the `resume_skill` taxonomy.

Use GET parameters for a progressive-enhancement server-rendered search.
This avoids making the initial release dependent on Cariera's vendor
AJAX script.

Use stable, namespaced query parameter names (for example
`c2eu_resume_keyword`, `c2eu_resume_location`, `c2eu_resume_category`,
`c2eu_resume_skill`) to avoid collisions with job-search filters and
existing WPJM query variables.

Validate every filter server-side. Escape values when rendering. Use
`WP_Query` or the Resume Manager's documented query API after inspecting
the installed plugin version. Do not assume undocumented API methods.

Search must: - Keep results restricted to active Candidate authors. -
Keep `post_status=publish`. - Support pagination. - Preserve active
filter values after submit. - Have a clear/reset action. - Show a
helpful empty state. - Avoid leaking private Resume data in search
snippets. - Be responsive and keyboard accessible.

Default order: newest published Resume first, unless the installed
Resume Manager's current default order is intentionally required.
Document the decision.

### 5.4 Resume card UI

Create plugin-owned markup and CSS with a namespace such as
`.c2eu-resume-directory`.

Suggested card fields: - Candidate photo (use Resume Manager/Cariera
candidate-photo helper where available, with a safe fallback). -
Candidate display name / Resume title. - Professional title. -
Location. - Resume category. - Skills (short, capped list). - Optional
experience summary only if a reliable public field exists. - View
Profile link.

Do not show private contact details or candidate email in the listing
card.

The whole card may link to the existing Resume permalink. Use
`get_permalink( $resume_id )` or the Resume Manager permalink helper. Do
not construct `/resume/{username}/` manually.

### 5.5 Pagination

Use standard WordPress pagination or a safe custom pagination renderer.
Preserve search parameters and ensure page numbers are validated.

If a custom AJAX experience is added later, it must use a nonce,
approved Employer authorization, bounded result count and the same query
constraints. AJAX is not required for the first release.

## 6. Single Resume: Contact Candidate workflow

### 6.1 Keep the existing Single Resume route

The single page is rendered by WP Job Manager -- Resume Manager's
`resume` CPT and Cariera's `content-single-resume.php` template
dispatcher. It is not a shortcode and does not need a new page.

Preserve Cariera's Resume content sections and existing layout selection
initially. The first implementation should focus on: - Approved Employer
access. - Removing/replacing Invite Candidate. - Adding the Click2EU
Contact button and form. - Consistent styling across V1, V2 and V3
layouts.

### 6.2 Replace Invite Candidate safely

Inspect the actual installed Cariera Core/Addons source to identify the
exact callback that outputs "Invite Candidate".

-   Remove only that exact callback from its exact hook/priority.
-   Do not use `remove_all_actions()` on shared Resume hooks.
-   Do not remove Download CV, bookmark, expiry, edit or unrelated
    Resume actions.
-   Add the new Click2EU Contact action in a stable hook/position.
-   Confirm behavior in all configured single Resume layouts (V1/V2/V3).
-   If the vendor action is not removable through a stable public hook,
    use a documented WP Job Manager template override/filter owned by
    the child theme only as a fallback. Prefer plugin hooks and avoid
    editing parent theme files.

The Contact button should render only for approved Employers and
administrators. Candidate authors viewing their own Resume should not
see it.

### 6.3 Contact popup/form fields

Suggested fields: - Employer name (pre-filled from current account;
read-only or editable according to product decision). - Company name
(pre-filled from verified user meta). - Employer email (pre-filled from
account email). - Subject. - Message.

The form should identify the target Resume internally using a hidden
Resume ID. Do not accept a destination email address from the browser.

### 6.4 Submission security

Implement a dedicated handler in the plugin. It may use a normal
POST/redirect flow initially; AJAX is optional.

Every submission must validate: - User is logged in. - User is an
approved Employer (or Administrator). - Nonce is valid. - Resume ID
exists and is `post_type=resume`. - Resume is published. - Resume owner
is a Candidate with effective Active membership. - Candidate's account
email is valid. - Message and subject pass length limits and
sanitization. - Rate limit / anti-spam guard passes.

Do not trust: - Hidden email fields. - Hidden Employer IDs. -
Browser-supplied company details. - A client-side role value. - A
client-side verification status.

Derive the Employer and Candidate from the authenticated user and Resume
author on the server.

### 6.5 Email delivery

Send two emails: 1. To the Candidate's WordPress account email
(`get_userdata( $resume_author_id )->user_email`). 2. To the site's
configured administrator email (`get_option( 'admin_email' )`).

If the product later explicitly requires using Resume Manager's
`_candidate_email`, decide a safe precedence rule and validate it.
Default recommendation: use the Candidate's account email to avoid an
arbitrary Resume meta address becoming the delivery destination.

Email contents: - Candidate greeting. - Employer name and verified
company name. - Employer reply-to email. - Subject and message. - Link
to the Employer's website/profile only if a trusted field exists. -
Resume link for Admin reference.

Set a safe `Reply-To` header to the Employer's verified account email.
Do not expose the Candidate email to the Employer in the response or
confirmation.

Admin copy should clearly identify it as an Employer-to-Candidate
contact request and include Employer user ID, Candidate user ID and
Resume ID.

Use `wp_mail()` and handle its return value. Do not claim inbox
delivery; report only that WordPress accepted or failed to accept the
message. If the first email succeeds but the second fails (or vice
versa), handle and log the partial result without silently claiming both
were delivered.

Add a reasonable rate limit per Employer and Resume (for example, a
short cooldown) and a general per-account limit. Avoid storing
unnecessary message content in logs.

### 6.6 User feedback

After successful submission, show a clear success notice: "Your message
has been sent to the Candidate."

On failure, show a safe error that does not reveal internal server
details.

Prevent accidental duplicate submissions with a one-time token or
short-lived idempotency key if feasible.

## 10. Migration and existing Employer accounts

Existing Employer accounts must not become automatically approved.

On first deployment: - Existing Employer with no verification status =\>
unverified/pending. - Existing Employer must be reviewed by Admin before
protected Employer access is granted. - Existing Candidate accounts

not bulk-approve based on company name or registration number alone.

If there is a large number of existing Employer accounts, provide a
controlled review workflow; do not silently approve them in an upgrade

## 11. QA and acceptance criteria

The code agent must create automated tests/integration assertions where
the current project test harness allows. Also provide a manual
Cariera-enabled browser QA checklist.

### 11.1 Employer registration and approval

-   Candidate registration works exactly as before.
-   Candidate registration does not show or require Employer company

-   Candidate cannot access Resume Directory even with Active

-   Approved Employer can access it.
-   Admin can access it.

# 14. Site Owner: step-by-step setup after the coding agent finishes

The coding agent must update these instructions to match the final
implementation. The steps below are the expected setup plan.

## Before installing

1.  Take a complete database backup.
2.  Back up `wp-content/plugins/click2eu-membership`.
3.  Use the local/staging Cariera-enabled site first.
4.  Confirm Cariera Core, Cariera Addons, WP Job Manager, Resume Manager
    and WooCommerce are active and licensed.
5.  Confirm the active plugin branch/release artifact and save its
    commit SHA.

## Install the updated plugin

1.  Download the release ZIP produced by the coding agent.
2.  In WordPress Admin, open **Plugins → Add New → Upload Plugin**.
3.  Upload the updated Click2EU Membership ZIP.
4.  If prompted, choose **Replace current with uploaded**.
5.  Activate/update the plugin.
6.  Confirm the plugin does not show a fatal error.
7.  Open **WP Admin → Click2EU Memberships** and confirm the new
    Employer Verification screen is available.
8.  Open the plugin Settings/Diagnostics screen and confirm Resume
    Manager and Cariera integrations are detected.

## Employer verification setup

1.  Open **Click2EU Memberships → Employer Verification**.
2.  Review the list of existing Employer accounts.
3.  Treat all existing accounts without an explicit Approved status as
    Pending/unverified.
4.  Verify each company registration manually using the business
    documentation/process chosen by Click2EU.
5.  Approve only legitimate Employers.
6.  Reject invalid applications or suspend accounts when necessary.
7.  Confirm an approved Employer can log in and a pending Employer
    cannot.

Do not turn on Cariera's global User Approval setting.

## Resume Directory page setup

1.  Open **Pages → All Pages**.

2.  Find the existing page titled **Resume** (the page currently
    containing `[resumes]`).

3.  Edit that page.

4.  Remove the old `[resumes]` shortcode.

5.  Add a Shortcode block/Elementor Shortcode widget containing exactly:

    `[click2eu_resume_directory]`

6.  Keep the existing page URL/slug and page ID.

7.  Update the page.

8.  Do not create a separate WordPress Page for each Candidate or Single
    Resume.

9.  Confirm the Resume page is still linked from the Employer navigation
    only. The navigation link is not a security control; server-side
    access checks must enforce the restriction.

## Single Resume setup

1.  Do not create a new page for `/resume/candidate-name/`.
2.  Do not add a shortcode to individual Candidate Resume URLs.
3.  The Resume Manager CPT and its existing rewrite/permalink system
    continue to resolve single Resume pages.
4.  Confirm the plugin's Contact button appears on a single Resume for
    an approved Employer.
5.  Confirm Invite Candidate is gone and unrelated Resume actions still
    work.
6.  Check the result for the active Cariera single Resume layout and, if
    layouts are selectable, test V1/V2/V3.

## Email setup

1.  Confirm WordPress Admin Email is correct under **Settings →
    General**.
2.  Confirm the site has a working SMTP/mail transport.
3.  Send a test Contact request from an approved Employer to a test
    Candidate.
4.  Confirm Candidate receives the message.
5.  Confirm Admin receives the copy.
6.  Confirm Reply-To points to the Employer.
7.  Confirm the Candidate email is not displayed to the Employer.
8.  Check spam/junk folders and SMTP logs if delivery is missing.

Remember: a successful `wp_mail()` return means WordPress accepted the
message for transport; it does not prove inbox delivery.

## Navigation setup

1.  Keep Resume navigation visible only to Employer accounts (and
    optionally Administrators).
2.  Keep it absent from Candidate navigation.
3.  Ensure pending/rejected/suspended Employers do not see it.
4.  Test the direct Resume page URL as Guest, Candidate, Pending
    Employer, Approved Employer and Administrator.

## Final acceptance checklist for the site owner

-   [ ] Candidate can register without company fields.
-   [ ] Candidate can log in without Admin approval.
-   [ ] Candidate membership purchase and access work as before.
-   [ ] Employer registration requires Company Name and Registration
    Number.
-   [ ] New Employer is Pending by default.
-   [ ] Pending Employer cannot log in or access Employer features.
-   [ ] Admin can approve/reject/suspend Employers.
-   [ ] Approved Employer can log in.
-   [ ] Resume page uses `[click2eu_resume_directory]`.
-   [ ] Resume search and pagination work.
-   [ ] Only active Candidate Resumes appear.
-   [ ] Candidate cannot open the Resume Directory.
-   [ ] Single Resume opens using the existing `/resume/.../` permalink.
-   [ ] Invite Candidate has been replaced by Contact.
-   [ ] Contact sends email to Candidate and Admin.
-   [ ] Candidate email is not exposed to Employer.
-   [ ] Direct URL and direct POST/AJAX access are protected.
-   [ ] Mobile layout is correct.
-   [ ] Existing membership, checkout, renewal, upgrade and notification
    tests pass.

3.  List of changed/added files.
4.  Explanation of how Employer registration fields were integrated.

    replaced.

8.  Any admin settings that must be configured.
9.  Exact test commands and results.

    identified.

flow, all protected Resume routes, Candidate regression tests, Contact
email workflow and real Cariera-enabled browser tests pass.
